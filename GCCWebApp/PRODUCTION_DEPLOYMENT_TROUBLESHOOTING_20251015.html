2. Root Cause Analysis

HTTP 500.19 errors are typically caused by one of the following server-side configuration issues:

Cause Likelihood Description
ASP.NET Core Hosting Bundle Not Installed HIGH Server needs ASP.NET Core 8.0 hosting bundle to run the application
IIS URL Rewrite Module Missing HIGH web.config uses URL rewrite rules which require this module
Application Pool Misconfigured MEDIUM App pool must be set to "No Managed Code" for .NET Core apps
File Permissions MEDIUM IIS app pool identity needs read/execute permissions on deployed files
.NET 8 Runtime Not Installed HIGH Server needs .NET 8.0 runtime to execute the application
IIS Feature Locks MEDIUM Shared hosting may have certain IIS features locked at server level
Web.config XML Syntax Error LOW Malformed XML (verified - file is correct)

4. Troubleshooting Steps

Step 1: Verify ASP.NET Core Hosting Bundle

1 Check if hosting bundle is installed

Contact AccuWebHosting Support

Since this is shared hosting, you'll need to contact AccuWebHosting support to verify or install the required components.

What to ask AccuWebHosting support:

  • Is the ASP.NET Core 8.0 Hosting Bundle installed on the server?
  • Is the IIS URL Rewrite Module installed?
  • What version of IIS is running? (Need IIS 7.5 or higher)
  • Are there any IIS feature locks that would prevent web.config settings?
  • Can they provide the detailed IIS error page (not just the log)?

Step 2: Verify Application Pool Configuration

2 Check IIS Application Pool settings

Required settings:

.NET CLR Version: No Managed Code Managed Pipeline Mode: Integrated Identity: ApplicationPoolIdentity (or custom account with appropriate permissions)

Step 3: Check File Permissions

3 Verify IIS can read deployed files

Required permissions for IIS app pool identity:

  • Read & Execute on all application files
  • Read on web.config
  • Write on logs folder (if exists)
  • Modify on App_Data folder (if exists)

Step 4: Get Detailed Error Information

4 Enable detailed IIS errors

Ask AccuWebHosting to temporarily enable detailed errors, or check if you can add this to web.config:

<system.webServer> <httpErrors errorMode="Detailed" /> </system.webServer>
Note

This may conflict with the existing httpErrors configuration. Use only for troubleshooting.

Step 5: Create Simplified Web.config

5 Test with minimal configuration

If certain IIS modules aren't available, try this minimal web.config:

<?xml version="1.0" encoding="utf-8"?> <configuration> <location path="." inheritInChildApplications="false"> <system.webServer> <handlers> <add name="aspNetCore" path="*" verb="*" modules="AspNetCoreModuleV2" resourceType="Unspecified" /> </handlers> <aspNetCore processPath="dotnet" arguments=".\GCCWebApp.dll" stdoutLogEnabled="true" stdoutLogFile=".\logs\stdout" hostingModel="inprocess"> <environmentVariables> <environmentVariable name="ASPNETCORE_ENVIRONMENT" value="Production" /> <environmentVariable name="DatabaseProvider" value="SqlServer" /> <environmentVariable name="USE_SQL_SERVER" value="true" /> </environmentVariables> </aspNetCore> </system.webServer> </location> </configuration>

This removes URL rewrite, security headers, and other features that might be locked. If this works, add features back one at a time to identify which is causing the problem.

5. Alternative Deployment Options

Option A: Self-Contained Deployment

If the server doesn't have .NET 8 runtime, republish as self-contained:

dotnet publish -c Release -r win-x64 --self-contained true -o ./publish-self-contained

This includes the .NET runtime in the deployment package (larger size but no server dependencies).

Option B: Framework-Dependent with URL Rewrite Removed

If URL Rewrite module isn't available, handle HTTPS redirection in the application code instead of web.config.

Option C: Different Hosting Provider

If AccuWebHosting doesn't support ASP.NET Core 8, consider:

  • Azure App Service (native ASP.NET Core support)
  • AWS Elastic Beanstalk
  • DigitalOcean App Platform
  • Dedicated Windows Server with full IIS control
