Current Data Model

This is how the database currently stores relationships:

Entity Relationships
Entity Relationship Target Notes
User Many-to-Many Company Via UserCompanies join table
User Many-to-Many Partner Via UserPartners join table
Certificate One-to-One Company (via CompanyId) Product belongs to a company
Certificate Enum Field Partner (Amazon/Novi/None) Certificate is tagged with partner
Company No Link Partner GAP: Companies are NOT linked to Partners
Certificate Enum (Single Value) Partner LIMITATION: Certificate can only have ONE partner (Amazon OR Novi OR None)
Key Issues:
  • The Partner entity and Company entity are completely separate. There's no way to automatically know which companies are "Amazon partners" vs "Novi partners" without manual configuration.
  • NEW: The Certificate.Partner field is an enum (single value). A certificate cannot currently belong to multiple partner programs (e.g., both Amazon AND Novi).

This is the confusing case that needs client clarification.
Scenario: Acme Corp IS an Amazon Climate Pledge partner

Jennifer Smith - Acme Corp (Amazon Partner Company)

Three Possible Approaches:

Option A: Company Association Only

Configuration: User.Companies = [Acme Corp], User.Partners = []

Filter: WHERE Product.CompanyId = AcmeCorpId

What Jennifer Sees
Cert #001 - Acme Corp Product A (Amazon)
Cert #003 - Acme Corp Product B (Novi)
Cert #005 - Beta Industries (Amazon) - HIDDEN

Result: Jennifer sees ONLY her company's certs, cannot see other Amazon partner companies.

Option B: Partner Association Only

Configuration: User.Companies = [], User.Partners = [Amazon]

Filter: WHERE Certificate.Partner = 'Amazon'

What Jennifer Sees
Cert #001 - Acme Corp Product A (Amazon)
Cert #005 - Beta Industries (Amazon)
Cert #012 - Gamma Tech (Amazon)
Cert #003 - Acme Corp Product B (Novi) - HIDDEN

Result: Jennifer sees ALL Amazon certs (including competitors), but NOT her own Novi certs.

Option C: Both Associations (OR Logic)

Configuration: User.Companies = [Acme Corp], User.Partners = [Amazon]

Filter: WHERE Product.CompanyId = AcmeCorpId OR Certificate.Partner = 'Amazon'

What Jennifer Sees
Cert #001 - Acme Corp Product A (Amazon)
Cert #003 - Acme Corp Product B (Novi)
Cert #005 - Beta Industries (Amazon)
Cert #012 - Gamma Tech (Amazon)

Result: Jennifer sees EVERYTHING - her company's certs AND all Amazon certs (most permissive).

Decision Needed

Which option is correct for a company representative whose company is an Amazon partner?

  • Option A - Keeps data isolated to their own company only
  • Option B - Treats them like Amazon staff (sees all Amazon certs)
  • Option C - Maximum visibility (both their company AND all Amazon certs)

Use Case: Multi-Partner Certificate

Potential Gap: Can a certificate belong to multiple partner programs?
Scenario: Product certified for BOTH Amazon AND Novi

Business Scenario: Acme Corp's "Eco Widget" product meets certification requirements for both the Amazon Climate Pledge program AND the Novi Connect program. The same certification applies to both.

Current System Limitation:

Current: Single Partner Only (Enum)

Database: Certificate.Partner is an enum field: Amazon | Novi | None

Problem: Must choose ONE partner - cannot select both

Current Workaround Options
Option 1: Create TWO separate certificates for the same product (duplicates data)
Option 2: Pick one partner, lose visibility for the other partner's users
Option 3: Set to "None" and use tags (loses partner filtering entirely)

System Design Options

Based on the use cases above, here are the implementation approaches:

Option 1: Keep Current System (No Changes)

How it works:

  • Admin manually sets User.Companies AND/OR User.Partners for each user
  • If user has both, OR logic applies (sees both sets of data)
  • No automatic relationship between Companies and Partners
Pros
  • No database changes needed
  • Maximum flexibility
  • Already implemented
Cons
  • Confusing for admin users
  • Easy to misconfigure
  • No clear rules for which to use when
Option 2: Role-Based Simplification
Recommended

How it works:

  • Partner role → User selects Partner ONLY (Company field hidden)
  • External Client role → User selects Companies ONLY (Partner field hidden)
  • Admin/Analyst roles → No selection needed (full access)
  • Role determines which association type applies
Pros
  • Clear, unambiguous rules
  • Simpler UI for user creation
  • Harder to misconfigure
  • Minimal database changes
Cons
  • Less flexible (can't have both)
  • May not cover edge cases
Option 3: Partner Hierarchy (Database Change)

How it works:

  • Add PartnerId column to Companies table
  • Companies can belong to a Partner (Acme Corp → Amazon)
  • User selects Partner → automatically sees all companies under that partner
  • OR user can override with specific company selection
Pros
  • Clear data hierarchy
  • Automatic company filtering
  • Scalable for many companies
Cons
  • Requires database migration
  • More complex implementation
  • What if company works with multiple partners?

Recommendation

Recommended: Option 2 - Role-Based Simplification

This approach eliminates confusion by making the role selection determine the data access type. Partner employees select a Partner. Company reps select Companies. No overlap, no ambiguity.

Implementation Summary:

Role Partner Selection Company Selection Data Filter
Admin Hidden Hidden All data
Analyst Hidden Hidden All data
Partner Required Hidden Certificate.Partner = X
External Client Hidden Required Product.CompanyId IN (...)
API Integration Optional Optional Configurable
Public Hidden Hidden Public certs only
Note: This recommendation assumes that company reps (even if their company is an Amazon partner) should only see their own company's data. If they need to see all Amazon partner data, they would need a Partner role instead.
