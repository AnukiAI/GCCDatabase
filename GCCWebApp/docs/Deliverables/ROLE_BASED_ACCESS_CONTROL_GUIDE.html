Executive Summary

The GCC Database Solution implements a robust, hierarchical role-based access control (RBAC) system with four distinct user roles, each with carefully designed permissions to ensure security, data integrity, and appropriate access levels for different user types.

Key Architecture

The RBAC system is implemented using ASP.NET Core's built-in authorization framework with custom policies defined in Program.cs. All controllers and actions are protected with [Authorize] attributes, and role claims are validated at runtime.

🔐

Authorization Policies

Four authorization policies control access throughout the application. These policies are defined in Program.cs (lines 224-252) and enforced via controller attributes.

Policy Name Required Roles Implementation Usage
AdminOnly Admin RequireClaim("Role", "Admin") User Management, Role Management, System Configuration
AnalystOrAdmin Admin Analyst RequireAssertion(Admin OR Analyst) Dashboard, Reports, Certificate CRUD (Read/Write)
ExternalAccess Admin Analyst External RequireAssertion(External OR Analyst OR Admin) Partner-specific certificate viewing, Limited exports
AuthenticatedUsers Admin Analyst External RequireAuthenticatedUser() General authenticated access, Profile management
Program.cs - Authorization Policy Configuration (Lines 224-252)
// ===== AUTHORIZATION POLICIES ===== builder.Services.AddAuthorization(options => { // Admin-only access options.AddPolicy("AdminOnly", policy => policy.RequireAuthenticatedUser() .RequireClaim("Role", "Admin")); // Analyst or Admin access options.AddPolicy("AnalystOrAdmin", policy => policy.RequireAuthenticatedUser() .RequireAssertion(context => context.User.HasClaim("Role", "Admin") || context.User.HasClaim("Role", "Analyst"))); // External, Analyst, or Admin access options.AddPolicy("ExternalAccess", policy => policy.RequireAuthenticatedUser() .RequireAssertion(context => context.User.HasClaim("Role", "External") || context.User.HasClaim("Role", "Admin") || context.User.HasClaim("Role", "Analyst"))); // Any authenticated user options.AddPolicy("AuthenticatedUsers", policy => policy.RequireAuthenticatedUser()); });

Critical Finding: External Role & Report View Access

⚠️

External Users CANNOT Access Dashboard or Report View

Key Finding: The Dashboard Controller (DashboardController.cs:12) uses the [Authorize(Policy = "AnalystOrAdmin")] attribute, which explicitly requires either Analyst OR Admin role. The External role is NOT included in this policy, meaning External users have NO ACCESS to the Dashboard or any of the 12 analytics metrics.

What External Users Get Instead

DashboardController.cs - LoadPublicDashboardData() for External Users (Lines 113-122)
private async Task LoadPublicDashboardData(DashboardViewModel model) { await _performanceMonitoring.MonitorAsync("Dashboard.LoadPublicData", async () => { // Limited view for external users var activeCerts = await _certificateRepository.GetActiveCertificatesAsync(); model.TotalActiveCertificates = activeCerts.Count(); model.RecentCertificates = activeCerts.Take(5); }); }

External users only receive:

  • Total Active Certificates (filtered to their partner)
  • Recent 5 Certificates (filtered to their partner)
ℹ️

Report View = Dashboard (Analyst/Admin Only)

  • 12 Statistical Metrics Cards
  • 5 Data Tables (Certificate Types, Top Companies, Status Distribution, Product Types, Categories)
  • 4 Chart Types (Monthly, Status, Company, Expiration)
  • CSV Export for individual stats and tables

Access: Analyst and Admin roles ONLY via AnalystOrAdmin policy.

Detailed Role Descriptions

1. Public Role (Unauthenticated)

Purpose: Provide public access to certificate verification database for consumers, retailers, and general public.

Certificate Access:

  • ✓ View public certificate tile view (/Certificate/CertificateTileView)
  • ✓ View certificate details (read-only, public information only)
  • ✓ Search and filter certificates
  • ✓ Use autocomplete search with categorized suggestions
  • ✓ Access shareable URLs for filtered searches
  • ✗ NO create, edit, or delete operations
  • ✗ NO export capabilities

Dashboard & Reporting:

  • ✗ NO Dashboard access
  • ✗ NO Report View
  • ✗ NO analytics metrics
  • ✗ NO chart data

Additional Access:

  • ✓ Home page
  • ✓ Privacy Policy
  • ✓ Error pages
  • ✗ NO authenticated features
Controller Authorization Example - Public Access
[AllowAnonymous] public IActionResult CertificateTileView() { return View(); }

2. External Role (Partner Access)

Purpose: Provide partner organizations (Amazon, Wayfair) with read-only access to their partner-specific certificates for integration and verification purposes.

Certificate Access:

  • ✓ View certificates filtered by partner association
  • ✓ Certificate Tile View (External) - Partner-filtered
  • ✓ Certificate Details - Partner certificates only
  • ✓ Search and filter (limited to partner data)
  • ✓ Export certificates (CSV) - Partner data only
  • ✗ NO Create/Edit/Delete operations
  • ✗ NO access to non-partner certificates

Dashboard & Reporting:

  • ✗ NO Dashboard Access - Dashboard requires AnalystOrAdmin policy
  • ✗ NO Report View - Full analytics not available
  • ✓ Limited statistics via LoadPublicDashboardData():
    • Total active certificates (partner-filtered)
    • Recent 5 certificates (partner-filtered)

Product Management:

  • ✓ Product Management (External View) - Read-only
  • ✗ NO Create/Edit products

Admin Functions:

  • ✗ NO User Management
  • ✗ NO Role Management
  • ✗ NO System Configuration
  • ✗ NO Admin pages (/Admin/*)
Controller Authorization Example - External Access
[Authorize(Policy = "ExternalAccess")] public IActionResult CertificateTileViewExternal() { // Certificates are filtered by partner in the repository layer return View(); }
⚠️

External Role Key Limitation

External users have READ-ONLY, PARTNER-FILTERED access. They cannot access the Dashboard (which requires AnalystOrAdmin policy), cannot create/edit/delete certificates, and all data they see is automatically filtered to their associated partner organization.

3. Analyst Role (Certificate Management)

Purpose: Empower GCC staff analysts with full certificate lifecycle management and comprehensive reporting capabilities without system administration privileges.

Certificate Management (Full CRUD - Except Delete):

  • ✓ Create new certificates (/Certificate/Create)

  • ✓ View all certificates (internal tile view)
  • ✓ Certificate workflow management (14-state lifecycle)
  • ✓ Transition certificate statuses
  • ✓ Upload certificate images
  • ✓ Full search and filtering
  • ✓ Export certificates (CSV/Excel/PDF)
  • ✗ NO Delete - Only Admin can delete

Dashboard & Reporting (FULL ACCESS):

  • ✓ Full Dashboard Access ([Authorize(Policy = "AnalystOrAdmin")])
  • ✓ All 12 Statistical Metrics
  • ✓ 5 Data Tables (Certificate Types, Top Companies, Status, Product Types, Categories)
  • ✓ 4 Chart Types (Monthly, Status, Company, Expiration)
  • ✓ Export individual statistics (CSV)
  • ✓ Export data tables (CSV)
  • ✓ Real-time data updates
  • ✓ Certificate statistics by type, status, company, product

Company & Product Management:

  • ✓ View all companies
  • ✓ Create/Edit companies
  • ✓ View all products
  • ✓ Create/Edit products
  • ✓ Product ID management (bulk import/export)

Admin Functions (NOT ACCESSIBLE):

  • ✗ NO User Management
  • ✗ NO Role Management
  • ✗ NO Certificate Types configuration
  • ✗ NO Product Types configuration
  • ✗ NO Certificate Fields management
  • ✗ NO Partners management

  • ✗ NO Tags management

Certificate Operations:

  • ✓ All Analyst certificate operations
  • ✓ Delete Certificates - Admin-only capability
  • ✓ Bulk certificate operations

Dashboard & Reporting:

Technical Implementation Details

Role Claims Storage

User roles are stored as claims in the authentication system and session storage:

Program.cs - Role Middleware (Lines 502-534)
// Role middleware - set session roles based on claims app.Use(async (context, next) => { if (context.User.Identity?.IsAuthenticated == true) { // Get role from claims and store in session var roleClaim = context.User.FindFirst("Role")?.Value; if (!string.IsNullOrEmpty(roleClaim)) { context.Session.SetString("UserRole", roleClaim); } // Get other user info var emailClaim = context.User.FindFirst("Email")?.Value; var nameClaim = context.User.FindFirst("Name")?.Value; if (!string.IsNullOrEmpty(emailClaim)) context.Session.SetString("UserEmail", emailClaim); if (!string.IsNullOrEmpty(nameClaim)) context.Session.SetString("UserName", nameClaim); } else { // Set default role for unauthenticated users context.Session.SetString("UserRole", "Public"); } await next(); });

Data Filtering by Role

Data access is filtered at the repository layer based on user role and partner association:

Repository-Level Filtering Example
public async Task<IEnumerable<Certificate>> GetCertificatesAsync(string userRole, string? partner) { var query = _context.Certificates.AsQueryable(); // Filter by partner for External users if (userRole == "External" && !string.IsNullOrEmpty(partner)) { query = query.Where(c => c.Partner == partner); } // Public users only see Active certificates if (userRole == "Public") { query = query.Where(c => c.Status == CertificateStatus.Active); } return await query.ToListAsync(); }

Session Management

User roles and information are stored in session for performance:

  • Session["UserRole"] - Current user's role
  • Session["UserEmail"] - User's email address
  • Session["UserName"] - User's display name
  • Session Timeout: 30 minutes idle
  • Session Cookie: HttpOnly, Secure (production), SameSite=Lax

Security Considerations

Defense in Depth

The RBAC system implements multiple layers of security:

Layer 1: Controller Authorization

  • [Authorize] attributes on controllers
  • Policy-based authorization
  • Role claim validation

Layer 2: Repository Filtering

  • Data filtered by role and partner
  • Query-level security
  • Prevent unauthorized data access

Layer 3: View-Level Security

  • UI elements hidden by role
  • Role-based navigation
  • Action buttons conditional

Layer 4: Session Security

  • HttpOnly cookies
  • Secure flag in production
  • 30-minute timeout
  • SameSite protection

Role Protection Rules

⚠️

Protected Roles & Users

  • Admin Role: Cannot be deleted from the system
  • Admin Users: Cannot be deleted (at least one Admin must exist)
  • Self-Deletion: Users cannot delete their own account
  • Role Escalation: Users cannot elevate their own role

Authentication Methods

Method Environment User Types Configuration
Azure AD B2C Production All authenticated users OpenID Connect, configured in appsettings.json
Cookie Authentication Development All authenticated users Fallback when Azure AD B2C not configured

JWT Bearer Production External API access Authorization: Bearer token

Best Practices Implemented

  • ✓ Principle of Least Privilege - Users get minimum necessary access
  • ✓ Defense in Depth - Multiple security layers (controller, repository, view)
  • ✓ Secure by Default - All controllers require authentication unless explicitly marked [AllowAnonymous]
  • ✓ Role-Based Filtering - Data automatically filtered by user role and partner
  • ✓ Session Security - HttpOnly, Secure, SameSite cookies with timeout
  • ✓ Audit Logging - All role-based actions logged for compliance
  • ✓ Protected Roles - Admin role and users cannot be accidentally deleted
