1. Overview

1.1 What Is Role-Based Access Control?

The GCC Database Solution uses Role-Based Access Control (RBAC) to manage what each user can see and do within the application. Instead of assigning individual permissions to each user, permissions are grouped into roles, and roles are assigned to users.

This approach provides:

  • Simplified administration — Manage access for groups of users, not individuals
  • Consistent security — All users in the same role have identical access
  • Audit trail — Easy to review who has access to what
  • Scalability — Add new users quickly by assigning an existing role
User ──> Role ──> Permissions ──> System Features │ ┌───────────────────────────────────────┘ │ ├── View Certificates ├── Create Certificates ├── Export Data ├── Manage Users └── ... (23 total permissions)

The system includes 23 permissions organized into 6 categories, with 4 built-in system roles and support for unlimited custom roles.

2. System Roles

The GCC Database ships with four system roles. These roles are protected and cannot be renamed or deleted, though their descriptions and permissions can be modified.

2.1 Administrator SYSTEM

Full system access and control. Administrators have unrestricted access to all features, settings, and data within the application.

Security Note: The Admin role grants complete system access including user management, data deletion, and system configuration. Assign this role only to trusted personnel who require full administrative control.

3. Custom Roles

Administrators can create custom roles to address specific access requirements that system roles do not cover. Custom roles offer full flexibility over permission assignment.

Custom roles CAN:

  • Be created with any name (up to 50 characters)
  • Have any combination of the 23 permissions
  • Be renamed after creation
  • Be deleted when no longer needed
  • Have their permissions modified at any time

Common custom role examples:

  • Partner — API read access + certificate view for integration partners (Amazon, Novi)
  • API Integration — API read/write for automated services
  • Report Viewer — Data export and reports only
  • Senior Analyst — Analyst + certificate delete

6. Step-by-Step Procedures

6.1 Navigating to Role Management

1

Log in to the GCC Database with an Administrator account.

2

In the top navigation bar, click Administration to expand the dropdown menu.

3

Select Role Management from the dropdown.

4

The Role Management page loads displaying all configured roles in a table.

Direct URL: /Admin/RoleManagement

6.2 Viewing Roles

The Role Management page displays a table with the following columns:

ColumnDescriptionSortable?
Role NameThe unique name of the roleYes (A–Z / Z–A)
DescriptionBrief explanation of the role's purposeYes
PermissionsFirst 3 permissions shown as badges; "+X more" if additional existNo
UsersCount of users currently assigned to this roleYes (numeric)
ActionsEdit and Delete buttonsNo

The footer displays the total number of roles (e.g., "Showing 5 roles").

6.3 Creating a New Role

Procedure: Add New Role

1

On the Role Management page, click the Add New Role button (top-right area next to Export).

2

The Add New Role modal dialog opens.

3

Enter a Role Name (required, maximum 50 characters). Choose a clear, descriptive name.

4

Optionally enter a Description (maximum 255 characters) explaining the role's purpose.

5

In the Permissions section, select the desired permissions by checking the boxes in each category. Use Select All or Clear All buttons for quick selection.

6

Review your selections carefully.

7

Click Save Role to create the role, or Cancel to discard.

8

A success notification confirms the role was created. The table refreshes automatically.

Tip: Permission categories are displayed in a 3-column grid on desktop, 2 columns on tablet, and 1 column on mobile. Each category shows its permissions with checkboxes and descriptions.

Form Field Reference

FieldRequired?Max LengthNotes
Role NameYes50 charactersMust be unique. Cannot be changed later for system roles.
DescriptionNo255 charactersRecommended for documentation purposes.
PermissionsNo—A role with zero permissions is valid but grants no access.

6.4 Editing a Role

Procedure: Edit Existing Role

1

Locate the role in the table. Use the search bar if needed.

2

Click the Edit button (pencil icon) in the Actions column.

3

The Edit Role modal opens, pre-populated with the role's current settings.

4

Modify the name (custom roles only), description, or permission assignments as needed.

5

Click Save Role to apply changes.

6

A success notification confirms the update. The table refreshes automatically.

System Role Editing: When editing a system role (Admin, Analyst, External, Public), the Role Name field is disabled (grayed out). A yellow warning banner appears: "This is a system role. The role name cannot be changed, but you can modify the description and permissions."

6.5 Deleting a Role

Procedure: Delete a Custom Role

1

Locate the role in the table.

2

Click the Delete button (trash icon) in the Actions column.

3

A confirmation dialog appears asking you to confirm the deletion.

4

Click Confirm to proceed or Cancel to abort.

5

The role is permanently removed. A success notification confirms the deletion.

Deletion Rules:
  • The Admin role can never be deleted (button is disabled).
  • Other system roles (Analyst, External, Public) show a warning before deletion is allowed.
  • Roles with assigned users should have those users reassigned to a different role before deletion.
  • Deletion is permanent — there is no undo.

6.6 Exporting Roles

Procedure: Export Roles to CSV

1

On the Role Management page, click the Export button.

2

A CSV file downloads automatically to your browser's default download location.

3

The file contains all roles with their names, descriptions, permissions, and user counts.

Export format: CSV only (per application standards). Excel, JSON, and PDF exports are not available from admin pages.

6.7 Searching & Sorting

Search

Type in the search bar above the table to filter roles in real time. The search checks against:

  • Role name
  • Description
  • Permission names

Search is debounced (300ms delay) for performance. Results update automatically as you type.

Sort

Click any sortable column header to sort the table. Click again to toggle between ascending and descending order. The current sort direction is indicated by an arrow icon in the column header.

8. Assigning Roles to Users

Roles are assigned to users through the User Management page, not through Role Management. Each user is assigned exactly one role.

Procedure: Assign a Role to a User

1

Navigate to Administration > User Management.

2

Click Add New User or Edit on an existing user.

3

Select the desired role from the Role dropdown.

4

If the role is External, also select the user's Company.

5

Click Save to apply the role assignment.

6

The user must log out and log back in for the new role to take effect.

One Role Per User: The system enforces a single role assignment per user. To give a user a unique combination of permissions, create a custom role with the desired permissions and assign it to that user.

9. Authorization & Access Policies

The application enforces access control through authorization policies that map to role names. These policies determine which pages and features each role can access.

Policy NameRequired Role(s)Protected Areas
AdminOnlyAdminAll Administration pages (User, Role, Company, Tag, Partner management, System Settings)
AnalystOrAdminAdmin or AnalystCertificate Create/Edit, Internal Tile View, Import, Workflow actions
ExternalAccessAdmin, Analyst, or ExternalExternal Certificate View, Company-scoped data access
AuthenticatedUsersAny authenticated userBasic application access, Dashboard
How it works: When a user logs in, the system stores their role as a claim in their authentication token. Each page and API endpoint checks this claim against its required policy. If the user's role does not satisfy the policy, they receive a 403 Forbidden response.

11. Best Practices

Principle of Least Privilege

Always assign the minimum permissions necessary for a user to perform their job. If a user only needs to view certificates and export data, do not give them edit or delete access. Create a custom role if no system role matches.

Use Descriptive Names and Descriptions

When creating custom roles, use names that clearly communicate the role's purpose (e.g., "Amazon Partner" rather than "Custom Role 1"). Always fill in the description field so other administrators understand the role's intent.

Regular Access Reviews

Periodically review role assignments to ensure they remain appropriate. Check the Users column in the role table to identify roles with no assigned users (candidates for cleanup) or roles with many users (candidates for review).

Avoid Modifying System Role Permissions Without Cause

System roles ship with carefully considered default permissions. Before changing a system role's permissions, consider whether a custom role would better serve your needs without affecting other users.

Document Changes

When creating or modifying roles, use the Description field to record why the change was made and by whom. This helps future administrators understand the rationale behind custom configurations.

12. Troubleshooting

Problem: User cannot access a feature they should have

Check 1Verify the user's role in Administration > User Management.
Check 2Verify the role has the correct permissions in Administration > Role Management.
Check 3Ask the user to log out and log back in. Role/permission changes require a new login session.
Check 4For External users, confirm their Company assignment matches the data they need to access.

Problem: Permission changes not taking effect

CauseUser's authentication session still has the old role claim cached.
SolutionThe user must log out and log back in. Permission changes are applied at login time, not in real time.

Problem: Cannot delete a role

If Admin roleThe Admin role is permanently protected and cannot be deleted under any circumstances.
If system roleSystem roles show a warning. You must confirm before deletion proceeds.
If users assignedReassign all users to a different role before deleting. Check the Users count column.

Problem: Cannot rename a role

CauseSystem roles (Admin, Analyst, External, Public) have immutable names. The name field is disabled in the edit modal.
SolutionSystem role names cannot be changed. If you need a differently-named role, create a new custom role with the desired name and permissions.

Problem: "Failed to create role" error

Check 1Ensure the Role Name is not empty (required field).
Check 2Ensure the Role Name is 50 characters or fewer.
Check 3Check for duplicate role names. Each role name must be unique.
Check 4Check the browser console for network errors (press F12).

Problem: Export button not working

CauseBrowser pop-up blocker may be preventing the file download.
SolutionAllow pop-ups for the GCC Database URL, or check your browser's download bar/folder.

13. Frequently Asked Questions

Q: Can a user have multiple roles?

A: No. The system enforces one role per user. If a user needs a unique combination of permissions, create a custom role that includes exactly the permissions they need.

Q: What happens if I change a role's permissions?

A: The change takes effect for all users assigned to that role after they log out and log back in. Currently logged-in users will continue with their existing permissions until their next login.

Q: Can I restore a deleted role?

A: No. Role deletion is permanent. You would need to recreate the role manually with the same name and permissions. Consider exporting roles before making deletions.

Q: Why can I change system role permissions but not their names?

A: System role names are used in authorization policies throughout the application code. Changing them would break access control. Permissions, however, can be safely modified because they are evaluated dynamically.

Q: What is the maximum number of roles I can create?

A: There is no hard limit on custom roles. However, for maintainability, keep the number of distinct roles manageable and well-documented.

Q: How do I see which users are assigned to a specific role?

A: The Role Management table shows the Users count for each role. To see the specific users, go to Administration > User Management and filter or sort by role.

Q: Are permissions checked in real-time or at login?

A: Role-based authorization is checked in real-time on every request using the role claim in the user's authentication session. However, the role claim itself is set at login time. So while every request checks access, the user must re-login after role changes for the new role to be reflected in their session.

14. Glossary

TermDefinition
RBACRole-Based Access Control — security model where permissions are assigned to roles, and roles are assigned to users.
RoleA named collection of permissions that defines what actions a user can perform.
PermissionA granular access right that controls a specific action (e.g., "Create Certificates").
System RoleA built-in role that ships with the application. Name is immutable; cannot be deleted.
Custom RoleAn administrator-created role with configurable name and permissions.
ClaimA piece of identity data (e.g., role name) stored in the user's authentication token.
PolicyAn authorization rule that specifies which roles can access a particular feature or page.
CodenameA machine-readable identifier for a permission (e.g., certificate.view).
WorkflowThe 14-state certificate lifecycle from Draft through Approved, Expired, etc.
Least PrivilegeSecurity principle: grant only the minimum access needed for a user to perform their duties.
