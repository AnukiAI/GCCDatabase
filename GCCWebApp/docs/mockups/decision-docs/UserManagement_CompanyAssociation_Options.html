User-Company Association Design

Evaluating the best approach for linking users to companies based on role and partner relationships

Current Data Model

User
→ many-to-many →
Company
← owns ←
Certificate
User
→ many-to-many →
Partner
✗ NO LINK ✗
Company

Problems with Current Design

  • No Partner→Company relationship - Partners (Amazon, Novi) aren't linked to the companies they work with
  • Manual company selection - If Amazon works with 50 companies, admin must manually select all 50 for each Amazon user
  • Maintenance nightmare - When a new company joins Amazon, must update ALL Amazon users
  • Error prone - Easy to miss companies or add wrong ones

Three Design Options

Option A: Keep Current

Direct User→Company Selection
NO DB CHANGES
User ──┬──→ Company₁ ├──→ Company₂ ├──→ Company₃ └──→ Partner (metadata only) * Companies selected individually * Partner is just a label

Pros

  • No database changes needed
  • Maximum flexibility
  • Already implemented

Cons

  • Tedious for many companies
  • No inheritance from Partner
  • Must update each user manually
  • Doesn't scale well

Option B: Partner Hierarchy

Partner owns Companies
RECOMMENDED
Partner (Amazon) ├──→ Company₁ ├──→ Company₂ └──→ Company₃ User ──→ Partner └──→ Inherits all companies! * User selects Partner * Automatically gets Partner's companies

Pros

  • Simple user creation
  • Automatic inheritance
  • Add company to Partner = all users get it
  • Scales perfectly

Cons

  • Requires DB migration
  • Must set up Partner→Company links
  • Less flexible (all or nothing)

Option C: Hybrid

Partner default + Override
MOST FLEXIBLE
Partner (Amazon) ├──→ Company₁ (default) ├──→ Company₂ (default) └──→ Company₃ (default) User ──→ Partner ├──→ Inherits defaults └──→ Override: [Company₁ only] * User gets Partner's companies by default * Can override to subset if needed

Pros

  • Best of both worlds
  • Default inheritance + flexibility
  • Handle edge cases
  • Future-proof

Cons

  • More complex logic
  • Requires DB migration
  • UI more complicated

Comparison Matrix

Criteria Option A (Current) Option B (Partner Hierarchy) Option C (Hybrid)
Database Changes None Add PartnerId to Company Add PartnerId + override flag
User Creation Speed Slow (pick each company) Fast (pick Partner only) Fast (pick Partner, optional override)
Adding New Company to Partner Update ALL users manually Automatic for all users Auto unless overridden
Flexibility Maximum All or nothing Maximum
Complexity Simple Simple Moderate
Scalability Poor Excellent Excellent
Best For < 10 companies per user Partners with many companies Complex enterprise scenarios

Recommendation

Option B (Partner Hierarchy) is recommended for your use case because:

  • Amazon, Novi are major partners with many companies
  • Users from a Partner typically need access to ALL that Partner's companies
  • Dramatically simplifies user creation workflow
  • Auto-updates when companies are added to Partners
  • Cleaner data model - Partner actually owns the relationship

Consider Option C if you have cases where Partner users need access to only SOME companies (e.g., regional managers, specific brand contacts).

Required Database Change

-- Add Partner→Company relationship
ALTER TABLE Companies
ADD PartnerId INT NULL
    REFERENCES Partners(Id);

-- Example: Associate Amazon's companies
UPDATE Companies
SET PartnerId = (SELECT Id FROM Partners
                 WHERE Name = 'Amazon')
WHERE Name IN ('ACME Corp',
               'GreenTech', ...);
