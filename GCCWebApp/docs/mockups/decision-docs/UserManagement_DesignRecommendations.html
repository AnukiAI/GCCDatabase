Design Recommendations

Professional analysis for User Data Access Architecture

Guiding Design Principles

Principle of Least Privilege

Users should only have access to the minimum data required for their role. When in doubt, restrict access.

Clear Role Boundaries

Each role should have a single, well-defined access pattern. Overlapping access creates confusion and security gaps.

Simplicity Over Flexibility

A simple system that's hard to misconfigure is better than a flexible system that's easy to get wrong.

Scalability

The design should work whether you have 10 companies or 10,000 companies, without manual per-user configuration.

1
Partner User Access Scope
When an Amazon employee (Partner role) logs in, should they see ALL certificates tagged with Amazon, or only certificates from specific companies they're assigned to?
Recommendation

ALL certificates tagged with their Partner (Amazon/Novi)

Rationale

  • Business Purpose: Partner employees (e.g., Amazon Climate Pledge team) need to verify compliance across their ENTIRE partner network, not just specific companies
  • Audit Capability: They need to see all certificates claiming their partnership to identify issues, validate claims, and ensure consistency
  • Simplicity: One Partner association instead of manually assigning dozens/hundreds of companies
  • Scalability: As new companies join the partner program, their certificates are automatically visible - no user reconfiguration needed
2
Company Rep Access (When Company is Amazon Partner)
When a company representative (External Client) from an Amazon partner company logs in, should they see only their company's certificates, or their company's certificates PLUS all Amazon-tagged certificates?
Recommendation

ONLY their company's certificates (regardless of partner tag)

Rationale

  • Least Privilege: A company rep only needs to see their own company's data - they have no business need to see competitor certificates
  • Competitive Sensitivity: Showing them all Amazon partner certificates would expose competitor data (other Amazon partners)
  • Clear Boundaries: "External Client" means company representative, not partner program administrator
  • Elevation Path: If someone truly needs partner-wide visibility, give them the Partner role instead - that's what it's for
3
Role Mutual Exclusivity
Should the Partner and External Client roles be mutually exclusive? Can a user have both associations simultaneously?
Recommendation

YES - Mutually exclusive. One role per user.

Rationale

  • Clear Security Model: Each role has ONE access pattern. No confusion about what a user can see.
  • Prevents OR Logic Expansion: Current system uses OR logic (Partner OR Company), which gives MORE access - that's backwards for security
  • Audit Clarity: When reviewing user access, you know exactly what they can see based on their single role
  • Edge Case Handling: If someone truly needs both types of access:
    • Option A: Create two separate accounts (one for each role)
    • Option B: Elevate to a higher role (Analyst) that has broader access
    • Option C: This is rare enough that it doesn't justify complicating the entire system
4
Company-Partner Database Relationship
Should we track which companies are associated with which partners in the database? If so, how?
Recommendation

YES - Add PartnerId to Company, but as METADATA only (not for access filtering)

Rationale

  • Reporting Value: Enables reports like "How many Amazon partner companies do we have?" without affecting access control
  • Data Integrity: Documents the real-world relationship between companies and partner programs
  • NOT for Filtering: User access should still be determined by Role + direct associations, not inherited through company→partner
  • Simple Schema: Single optional PartnerId on Company (not many-to-many) - a company's "primary" partner program

Proposed Schema Addition

-- Add to Companies table (optional, nullable)
ALTER TABLE Companies
ADD PartnerId INT NULL
    REFERENCES Partners(Id);

-- Example data:
-- Acme Corp: PartnerId = 1 (Amazon)
-- Beta Industries: PartnerId = 1 (Amazon)
-- Gamma Tech: PartnerId = 2 (Novi)
-- Delta Mfg: PartnerId = NULL (no partner program)

-- NOTE: This is for REPORTING only
-- User access is still controlled by:
--   Partner role → Certificate.Partner field
--   External role → User.Companies association
5
Real-World Example of Both Associations
Can you think of a legitimate use case where a user would need BOTH Partner AND Company associations?
Recommendation

NO legitimate use case exists that justifies the complexity

Analysis

  • Partner Employees: Need partner-wide visibility → Partner role is sufficient
  • Company Representatives: Need company-specific data → External Client role is sufficient
  • Hypothetical "Both" Scenario: "Amazon employee who also represents Acme Corp"
    • This person is wearing two hats - they should pick one
    • If they're acting as Amazon, they use Partner access
    • If they're acting as Acme Corp, they shouldn't see other Amazon partner data
    • Having both simultaneously creates a security gray area
  • If Client Provides Example: We should evaluate whether:
    • The scenario is truly common enough to warrant system complexity
    • It could be solved with a higher role (Analyst)
    • Separate accounts would be more appropriate
6
Multi-Partner Certificates
Can a single certificate belong to multiple partner programs simultaneously? (e.g., both Amazon AND Novi)
Recommendation

YES - Support multi-partner certificates (requires database change)

Rationale

  • Real-World Scenario: A product certification may legitimately qualify for multiple partner programs (e.g., meets both Amazon Climate Pledge AND Novi Connect requirements)
  • Avoid Duplicate Data: Without multi-partner support, users must create separate certificates for the same product - leading to data duplication and sync issues
  • Partner Visibility: Both Amazon and Novi users should see a certificate that applies to their program
  • Future-Proof: As more partner programs are added, the limitation becomes more problematic

Required Database Change

-- CURRENT: Enum field (single value)
Certificate.Partner = Amazon | Novi | None  -- Can only pick ONE

-- PROPOSED: Many-to-many relationship
CREATE TABLE CertificatePartners (
    CertificateId INT REFERENCES Certificates(Id),
    PartnerId INT REFERENCES Partners(Id),
    PRIMARY KEY (CertificateId, PartnerId)
);

-- Example:
-- Cert #001 (Eco Widget): Partners = [Amazon, Novi]
-- Cert #002 (Green Item): Partners = [Amazon]
-- Cert #003 (Basic Product): Partners = []  -- No partners
UI Impact:

The Partner dropdown on Add/Edit Certificate would change from a single-select dropdown to multi-select checkboxes.

Implementation Steps

1

Update User Management Modal

Show Partner selector OR Company selector based on selected role (not both simultaneously)

2

Simplify User.Partners Relationship

Change from many-to-many to single Partner (a Partner user belongs to ONE partner: Amazon OR Novi)

3

Add PartnerId to Companies Table

Optional field for reporting purposes - indicates which partner program the company belongs to

4

Remove OR Logic from Data Filtering

Each role type uses ONE filter method only - no combining Partner + Company filters

5

Update Validation Rules

Partner role requires Partner selection. External role requires Company selection. Cannot have both.

6

Enable Multi-Partner Certificates (if approved)

Replace Certificate.Partner enum with CertificatePartners join table. Update Add/Edit Certificate UI from dropdown to checkboxes.

Document Purpose: Design recommendations for client review

These recommendations follow security best practices (least privilege, clear boundaries, simplicity)
