Four items, one defect

The client’s 9 September email reads as four bug reports. Measured against our own change-request process it is one defect, one question, and two scope changes — and the difference is worth money.

Source CR_9_9_26_edit.pdf Received 9 Sep 2026, 10:52 Status Draft — not sent

The ruling, item by item

01 Edit button should open a new tab Nothing in the baseline says how Edit navigates. Preview opens a tab; Edit was never specified either way, so no delivered requirement is missing. It works as built — the design is just awkward. UX
02 List view as the default for logged-in users The tile view is the specified default and the project’s headline feature. Changing it is new scope; remembering each person’s last choice is new functionality outright. CR — price it
03 Is the Certificate # column there for editing existing certs? Yes. The import is an update-or-create: blank assigns a new number, a supplied number updates that certificate after a preview diff. Nothing to change — but the answer exposes a data condition. Question
04 “Certificate Number is required” in the import modal The screen states a rule the system does not enforce. The baseline says a blank number auto-assigns; the interface tells users the opposite. The other import screen already says it correctly, so the two screens contradict each other. Defect

Reserved tracking IDs: CR-048 (item 1, if logged) · CR-049 (item 2) · DEF-416 (item 4). None are written to the registers yet.

How I decided

Not by judgement — by the test already written into docs/governance/change-request-process.md §B1:

Point at the line in the baseline that this request says was not delivered. If you can, it’s a Bug. If you cannot, it’s a CR. “The client assumed it” is not a line in the baseline. Change Request Process, Part B — Per-request triage

Only item 4 survives that test as a defect. For items 1 and 2 there is no line to point at, because the behaviour was never specified in the first place.

The same document flags precisely the trap this email sets: “New requirements arrive dressed as defects. A single QC log entry once carried 44 items, of which 39 were new requirements.” Triage runs per item, never per email.

Why the labels matter

The client offered to log all four in the QC log for tracking. If they go in as defects, two change requests get absorbed without ever being priced — and §C1 of the same process is blunt about the cost:

Absorb work silently and that number is zero, no matter how much you gave away. Phase 1’s absorbed CRs are, financially, indistinguishable from work that never happened. Change Request Process, Part C — Pricing

Absorbing items 1 and 2 is entirely reasonable — both are small and the goodwill is worth having. The process only asks that they be numbered, estimated, and recorded as absorbed, so the total value given away this phase is a real figure at renewal rather than a memory.

Flagged — answering item 3 surfaced this

Certificate numbers are not unique in the current data. The import matches an existing certificate by number and takes the first match. Where a number sits on more than one record — and a number of them do — an edit-by-import updates whichever record comes back first, which may not be the intended one.

This is a condition of the data, not a fault in the import, so it carries no defect number. But if the team is going to use the template routinely for edits, the safe answer is a check that stops and warns on an ambiguous number instead of quietly choosing. That would be its own small change request.

What I need back before anything is built

Three from the client, one from you:

  1. Item 1 — how far does the new tab reach? The tile card, the list row and the certificate detail page all run through one shared function, so they change together unless the detail page is deliberately excluded. Confirm which is wanted.
  2. Item 2 — hard default, or remembered preference? A fixed List default solves it for the analysts and hands the same complaint to anyone who prefers tiles. Remembering each person’s last choice solves it for everyone, and is the recommendation.
  3. Item 2 — internal team only, or external and partner logins too? “All logged in users” reads both ways. The draft assumes the internal team only.
  4. For you: the three tracking IDs above are reserved, not logged. If the reply goes out as written they need register rows, or the numbers will drift — re-grep both registers immediately before appending.

Draft reply

Hi Carly,

Thanks — this is exactly the kind of feedback that’s easiest to act on. I went through all four items against the code before answering. Two are straightforward changes, one is a question I can answer for you right now, and one is a genuine fault on our side.

1. Edit button opening in a new tab — yes, and it’s a small change

You’re right that this is the low-risk version of the fix. All three Edit buttons your team sees — on the tile card, in the list’s Actions column, and on the certificate detail page — run through a single shared piece of code, so changing one place changes all three and leaves everything else alone.

Two things to confirm before I build it:

  • Should Edit behave exactly like Preview does today — new tab, original tab untouched with the search results still on screen? That’s my assumption.
  • Any objection to it applying on the certificate detail page too? It’s consistent, but it’s a slightly different moment than the one your team described, so say if you’d rather I left it alone.

2. List view as the default — yes, with one question back

Easy change, low risk. Before I make it, though: the complaint is having to toggle each time the page loads, and there are two ways to solve that.

  • Hard default to List. Every page load starts in List, for everyone. Literally what you asked for. The catch is that it moves the problem — anyone who prefers tiles now toggles every time instead.
  • Remember each person’s last choice, starting everyone on List. First visit lands on List; after that the page opens in whichever view that person used last. Nobody toggles repeatedly. A bit more work, but not much.

I’d recommend the second — it settles the complaint rather than reassigning it. One caveat either way: the preference is remembered per browser, so someone moving to a different computer starts on List again.

Also worth confirming: does this apply to your internal team only, or to external and partner logins as well? My assumption is the internal team.

3. The Certificate # column in the template — your read is exactly right

That column is there for precisely the case you described. The import works as an update-or-create:

  • Leave Certificate # blank — the system assigns the next number and creates a new certificate.
  • Enter an existing certificate’s number — the import updates that certificate rather than creating a duplicate. Before anything is written you get a preview showing a field-by-field comparison of what will change, so you can back out if it isn’t what you expected.

No change needed here.

One thing I do want to flag, because it affects how safely the team can lean on this. Certificate numbers in the current data are not all unique — some numbers appear on more than one record. If someone imports a row using one of those, the system updates the first matching record it finds, which may not be the one they meant. That is a condition of the data rather than a fault in the import, and it may never come up. But if the team is going to use the template routinely for edits, I’d suggest we add a check that stops and warns when a number matches more than one certificate, instead of quietly picking one. Happy to scope that separately if you’d like it.

4. The “Certificate Number is required” text — you’re right, and I’ll fix it

Confirmed, and this one is ours to correct. Certificate # is not required when adding new entries, exactly as you found. Worth knowing that the other import screen in the application already describes the behaviour correctly, so the two screens currently contradict each other. I’ll bring the modal into line and make the wording spell out both cases — blank creates, filled updates.

I’m logging this as a defect rather than a change request, since it is incorrect instructions rather than new functionality.

On testing

Completely understood on not wanting to test the import against live data. When you’re ready I can walk the team through it on a copy so they can watch the preview-and-confirm step for themselves. Nothing is written until someone approves the diff — but that is much easier to trust once you have seen it happen.

Short version: item 3 needs nothing from us, item 4 I’ll fix, and items 1 and 2 I’ll build as soon as you confirm the questions above.
