### Gate 10 found something, and it was not a false alarm

The first rebuild (`20260917-1539`, 345 entries) shipped **five** `appsettings.*.template.json`
files. The pubxml had excluded only `appsettings.Production.template.json`; the other templates were
never covered, and two of them — `appsettings.Secrets.template.json` and
`appsettings.Secrets.test-site.template.json` — **have shipped in every bundle to date, including the
live one.**

No passwords: every credential in them is a placeholder. But their prose names real infrastructure —
the SMTP host `accumail3.accuwebhosting.com`, a server IP, the only real mailbox, and in the
test-site template a **live DB host and port**. That belongs nowhere near the web root.

Two changes, both made before this bundle was cut:

1. `PleskTestEnvironment.pubxml` now removes `appsettings.*.template.json` as a glob.
2. `verify-bundle.py` gained a **fatal** hygiene predicate for the same pattern, so the exclusion
   cannot be silently lost again. **Proven to fire:** it reports `[FAIL] appsettings.*.template.json: 5`
   against `20260917-1539` and `0` against this bundle.

**Left for a human, and now a required step:** the two Secrets templates already on the server. An
extract-over will not remove them. **Upload step 6** deletes them, with the
`appsettings.Production.json` warning attached.

### Gate 10, second finding: a `.bak` file was shipping

Comparing a **clean-clone publish** against the `1545` bundle (the DEF-429 closure step, below)
surfaced `wwwroot/css/certificate-create.css.bak` — present in the zip, absent from a fresh
checkout. It is an **untracked** local leftover from 2025-11-10 that the SDK's default content glob
picks up.

Low impact on the server: the static-files middleware has no content type for `.bak`, so it 404s.
The real problem is that **the bundle was not reproducible from git** — a file existed in the deploy
that no clone could produce, which is precisely the property that makes "what is actually running"
answerable. Two fixes, both before this bundle was cut:

1. `PleskTestEnvironment.pubxml` now removes `**\*.bak`, `**\*.orig` and `**\*~`.
2. `verify-bundle.py` gained a **fatal** "editor/backup leftovers" predicate. **Proven to fire:**
   1 hit against `1545`, 0 against this bundle.

The local `.bak` file is left on disk untouched — it is Shawn's to delete or keep, and the exclusion
means it no longer matters either way.

### DEF-429 closed out: the profile is now checked, and proven from a clean clone

Two halves, both done:

**(a) The gate asserts the policy, not just the bundle.** `verify-bundle.py` gained a
`PUBLISH PROFILE POLICY` section that reads the profile *from the tree* — a zip cannot show what its
own build was allowed to include — and asserts all five protections: `wwwroot\uploads`,
`App_Data\uploads`, `appsettings.Development.json`, `appsettings.*.template.json`, and
`EnvironmentName=Production`. **A missing profile is itself a FAIL**, because that is the state a
fresh clone was in before DEF-429.

Substring checks, deliberately not regex: the patterns contain Windows path separators, and an
escaping mistake in a gate is worse than no gate — it fails open and reads as a pass.

**Proven to fail on three known-bad inputs** (run against temp copies, never the real profile):

| Injected fault | Gate |
|---|---|
| `wwwroot\uploads` exclusion deleted — the 2026-04-23 wipe condition | **FAIL** OK |
| `EnvironmentName` switched to `Test` — breaks DB + B2C on the server | **FAIL** OK |
| profile absent entirely — the pre-DEF-429 fresh-clone state | **FAIL** OK |

**(b) A publish from a clean clone.** The staged tree was extracted to a fresh directory and
published with the same profile and configuration the deploy script uses. **Exit 0, 334 files**, and
0 hygiene failures: no DataProtection keys, no dev config, no `*.template.json`, no uploads tree, no
`Scripts/`, `docs/`, `docs2/` or test projects. `GCCWebApp.dll`, `web.config` and `appsettings.json`
all present.

**The one difference, and it is correct:** `appsettings.Production.json` is **absent** from a clean
clone, because it is gitignored (`.gitignore:48`) and carries a real DB password and a real signing
key. It must stay out of git. So a fresh clone builds a **complete application** but not a
**deployable bundle** — the production config is an operator-supplied file, which is the intended
arrangement, not a gap. Recorded here so nobody later reads its absence as a fault.

> **Method note.** The first clean-clone attempt failed with eight `MSB3030 Could not copy` errors
> and looked like a repo defect. It was not: the scratch path was **288 characters**, past Windows'
> 260-char `MAX_PATH`. The files existed — `ls` found them, Python's `os.path.exists` did not. Re-run
> from a short path, it published first time. **A build failure on a long temp path is an artifact
> until proven otherwise.**
