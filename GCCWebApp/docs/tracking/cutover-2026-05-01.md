## SQL backfill — STATUS: RAN 2026-05-01 (ahead of app deploy)

**Result on prod (`gccwebap_certificates` @ 68.71.129.120,1533):**
- Pre-flight: 17 product IDs on `Client Approved - Paid` certs (already `Active` — no change), 4 product IDs on `Expired` certs (incorrectly `Active` — flipped to `Inactive`).
- Backfill output: `CR-015 backfill: 0 rows -> Active, 4 rows -> Inactive.`
- Post-flight audit query: 0 rows (full compliance).
- Final state: 17 `Active` on `Client Approved - Paid`, 4 `Inactive` on `Expired`. No other cert statuses currently exist with product IDs on prod.

**Sequencing note:** Backfill ran ahead of the app code deploy. This is fine because:
1. The 4 flipped rows were all on Expired certs. The Partner API list endpoint already filters certs to `PublicStatuses` (DEF-097, 2026-04-21), so Amazon never received these stale `Active` rows regardless.
2. Old code on prod doesn't have the cascade, but it also doesn't actively re-flip rows. The only way a row could drift back to `Active` between now and the app deploy is if an analyst explicitly picks `Status = Active` on the (still-present) Product ID Manager UI in the old code. Mitigation: keep the deploy window short. Once the new code deploys, the Status field is removed from the UI entirely.
3. Backfill is idempotent — re-running after the app deploy is a safe no-op verification.

## SQL backfill — original section (run AFTER step 6 smoke-tests pass)

CR-015 needs a one-time backfill to align existing per-row Status with the new cascade rule.

- **Script:** `Scripts/database/CR015_backfill_product_id_status.sql`
- **Idempotent:** yes — safe to re-run; rows already in sync are no-ops.
- **Wraps:** single transaction; failure rolls back automatically.
- **Run command:**
  ```
  sqlcmd -S <prod sql server> -d GCCDatabase_Prod -U <user> -P <pass> \
    -i Scripts/database/CR015_backfill_product_id_status.sql -b
  ```
- **Expected output:** `CR-015 backfill: <N> rows -> Active, <M> rows -> Inactive.` Compare to pre-flight count.
- **Post-flight verification:** run the audit query at the bottom of the script header. Must return 0 rows.

If the script returns an error, do not proceed — leave the app running but flag for investigation. The cascade in app code will quietly converge over time as analysts edit certs, but the bulk of stale rows won't get fixed until the script runs.

## Rollback plan

If a smoke-test failure can't be resolved in 15 minutes:

1. Stop the IIS app pool.
2. Restore the **previous publish folder** (Plesk usually keeps the prior deploy in `httpdocs.bak/` or similar — confirm with the hosting team).
3. **Do not** restore the DB unless the CR-015 backfill ran AND a Critical bug surfaces. The backfill is reversible by re-running it after a code rollback (the cascade rule is the same in old code paths that don't run cascade — old code just won't keep them in sync going forward).
   - To revert backfilled rows: there's no automated reverse script; the most pragmatic recovery is to reapply the backfill once code is fixed forward. A DB restore is overkill and costs uploaded-data drift since the snapshot was taken.
4. Start the IIS app pool on the rollback build.
5. Confirm partner API list endpoint still returns `status: "Active"` (DEF-097 ships in the rolled-back build too, so the contract doesn't regress to leaking lifecycle statuses).
6. Open a defect for the failed item; this build re-spins after fix.

**Do NOT roll back uploads** — uploads were never modified by this deploy (excluded from the publish zip).
