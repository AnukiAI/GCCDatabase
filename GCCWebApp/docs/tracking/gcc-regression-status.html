What passed — and what that actually proves

A pass count is only worth what the assertion behind it demanded.

Access control — 168 of 168

Every one of 24 routes was requested by all seven callers: anonymous, External ×2, Partner ×2, Analyst, Admin. Public routes served anonymously; every External-, Analyst- and Admin-gated route bounced everyone below its policy to /Account/Login or /Account/AccessDenied and served 200 to those at or above it. No route leaked, and no route over-blocked.

Isolation — proven by pairing, not by counting

test.external (Sika Corporation) and test.external2 (MAPEI) were each walked to exhaustion and their certificate-number sets compared in both directions: 30 vs 21, zero shared, each seeing exactly one distinct company name. Same for the Amazon / Novi partner pair. A matching count would have survived a scoping bug; a set comparison does not.

Analyst and Admin see the identical internal population — 5,702 rows, zero rows exclusive to either. The anonymous population (964) is a strict subset of the internal one, with no certificate visible publicly that is absent internally.

The write path works end to end

As Analyst, through the real form: create → auto-numbered 26-0482 → PDF uploaded and linked → read back through the API → Draft correctly not publicly visible → Edit form prefilled with stored values → edit persisted → no duplicate row created → Delete correctly refused to the Analyst → deleted as Admin → fixture removed. The optional Certification Results field round-tripped correctly on both create and edit.

Findings

Seven findings. Numbered because the triage table at the end refers back to them.

F-1

Test-environment gate password rotation never took effect

Premise corrected

The 17 Aug rotation to GreenCircle-Test-2026 is not live. That value returns 401; the pre-rotation Cert-Test-Access-2026! still opens the gate.

Corrected 26 August — the impact claim here was wrong This originally said all 46 scripts had been rotated and were therefore failing at the gate. They had not been: 92 files under Scripts/ already carry the working Cert-Test-Access-2026!, and the only file with the non-working value was the regression-lib.js written during this run. The existing suite was never broken. The rotation exists in intent only — it reached neither the deployed config nor the scripts.

A deliberately-wrong password returns a clean 401 "Incorrect password", proving CSRF, data protection and the compare path are all healthy. The configured value simply is not the one running. TestEnvironmentGateMiddleware binds its options once in the constructor and is a singleton, so an app-pool recycle is required — editing the JSON alone does nothing. The DEF-363 recovery may also have restored the older appsettings.Production.json.

DecisionThe rotation is deliberately deferred while UAT users are mid-test. The regression lib was pinned to the live value instead. When the rotation does happen it needs an app-pool recycle as well as the config edit, because the middleware binds its options once in the constructor and is a singleton.

F-2

Amazon partner tile view shows two certificates ~2 months before their effective date

Fixed · DEF-376

The finding most worth acting on before the client demos the partner surface.

For test.amazon, the tile view returns 210 certificates while the CSV export returns 208. The two extra rows are:

Cert #CompanyStatusEffectiveExpires
26-0441X-SENSEClient Approved - Paid2026-10-212027-10-20
26-0442X-SENSEClient Approved - Paid2026-10-212027-10-20

Both are not yet effective — the run date is 25 Aug 2026.

DEF-358 established that the not-yet-effective gate applies to anonymous public plus the partner/Amazon surface. It was wired into the v1 partner API (all nine gate sites) and, by DEF-359, into the Active Product Identifiers export. Models/CertificateVisibility.cs records that CertificateTileExternalApiController was excluded deliberately — correct for the External / owning-company role, which should see its own upcoming certs. But that controller also serves the Partner role, which should not.

The evidence lines up exactly: DEF-359's own note records the Amazon partner API's clean set as 208 rows — the same 208 the export returns today. The tile view is the outlier.

  • Query filter — CertificateTileExternalApiController ~line 222: tests publishable status + expiration, no effective date.
  • Download gate — same controller, line 717: same omission.
  • By contrast CertificateController.cs:2392 does gate Partner on IsNotYetEffective.
Fixed — DEF-376 query.WhereEffectiveDateReached() now runs in the Partner branch only, with a matching IsNotYetEffective guard on the download action so the PDF cannot be pulled by id either. Lower bound only, same reasoning as DEF-359. External/company behaviour is unchanged.

Verified on localhost signed in as a real Partner user scoped to Amazon: tile population 208 (was 210), 26-0441 and 26-0442 absent, zero not-yet-effective rows, tile count now equal to the export count, and the download of 26-0441 returns 400 “Certificate is not available for download”.
F-3

Novi partner's certificate export returns HTTP 400

Fixed · DEF-377

test.novi requesting /Certificate/ExportCertificates?format=csv receives HTTP 400, text/plain, "No data to export or export failed".

A partner with zero associated certificates should get an empty CSV (header row only) or a friendly empty state — not a client-error status with a message that conflates nothing to export with the export failed. This is the same broad-catch anti-pattern already called out on ExportController.cs:227 under DEF-359 and DEF-360.

Fixed — DEF-377 An empty result set now flows into the CSV generator, which writes the header before it iterates, so the caller gets a valid header-only file. null now means failure only, and the controller returns 500 for it rather than 400.

Verified on localhost: an export filtered to match nothing returns 200, text/csv, exactly one line. A genuine SQL execution timeout on the same endpoint was separately observed to surface as 500 — which is the behaviour DEF-360 asked for.
F-4

Import rejects a blank Certificate #, while the Create form auto-numbers one

Fixed · DEF-378

Two write paths disagree about the same field:

PathBlank Certificate #
/Certificate/CreateAuto-numbers. Verified — generated 26-0482.
CSV importRejects. "Certificate Number is required", whole import blocked.

The import template annotates the Status column with "defaults to Draft if blank" but marks nothing on Certificate #, so an analyst has no way to know it is mandatory until the import is refused. Auto-numbering is an original requirement.

Fixed — DEF-378 · import now auto-numbers A blank Certificate # is no longer an error; the number is minted at apply time (not preview, which would reserve a number the analyst might never use) via the same repository method the Create form uses, so the DEF-322 four-digit rule and the year-rollover behaviour cannot drift.

A third bug surfaced while fixing it: rows were grouped by certificate number to support multi-ASIN rows, so every blank-numbered row collapsed into one group and two blank rows imported as ONE certificate. The grouping key is now a tuple carrying the row index for blank rows.

A number supplied in the file still wins — which is how the initial data migration keeps the client’s existing numbers. Accepted trade: a blank-numbered row cannot take part in multi-ASIN grouping, since there is no shared key to group on.

Verified through the real upload → preview → apply path: a two-row file with both numbers blank previews as 2 new / 0 errors showing (auto-assign), applies, and produces 26-0482 and 26-0483 — two distinct numbers.
F-5

Product import template is downloadable by External and Partner users

Fixed · DEF-379

/Product/DownloadProductImportTemplate returned HTTP 200 / text/csv to test.external, test.external2, test.amazon and test.novi. ProductController carries a class-level [Authorize(Policy = "ExternalAccess")] and this action adds no further attribute, while the matching ImportProducts action is AnalystOrAdmin.

No data leaks — it is an empty column-header template. But it hands an import affordance to roles that cannot import, which cuts against the "External users get no Add/Edit affordances" rule. The certificate import template is correctly gated; only the product one is not.

Fixed — DEF-379 [Authorize(Policy = "AnalystOrAdmin")] added to the action. Verified on localhost: Admin still receives the CSV (200); an unauthenticated caller is bounced to /Account/Login (302).
F-6

Novi has zero certificate associations anywhere in the database

Data / coverage

Across all 5,702 certificates the partner field holds only Amazon (244) and blank (5,458). No certificate is associated with Novi, Wayfair or Other.

This is why test.novi sees nothing, and it is correct behaviour given the data — partner scoping runs the certificate-level association first, so a partner with no associations reaches nobody. A data gap, not a code defect.

The consequence is a test-coverage hole: the Novi path is entirely unexercised, so the Amazon/Novi pair currently proves only "Amazon sees Amazon" and "Novi sees nothing" — it cannot prove Novi is correctly denied Amazon's rows.

RecommendationSeed a handful of Novi associations on TEST to close the gap.

F-7

Duplicate certificate numbers are live on TEST

Already DEF-369

137 certificate numbers are shared by 312 rows (5,702 rows → 5,527 distinct). Eight of those numbers, covering 20 rows, are publicly visible. Examples: 26-0182 ×4, 26-0166 ×3, 26-0168 ×3.

312 − 137 = 175 surplus rows, matching DEF-369's "175 certificates have no URL at all" exactly. This is the known migration blocker, confirmed live rather than a new defect.

ActionNone — recorded as regression evidence that it survived the migration. No new DEF needed.

Open question for the client

Not a defect. Flagged because the numbers are dramatic enough that the client will ask.

Should an External (owning-company) user see their own expired certificates?

Today they cannot. Sika Corporation has 574 certificates in the database; test.external sees 30. MAPEI has 313; test.external2 sees 21.

That is as-coded and deliberate — CertificateTileExternalApiController filters External users to publishable statuses and unexpired. Given the status profile below, the effect is that a company sees roughly 5% of its own record.

DEF-358's scope note says External users keep seeing upcoming certificates because "a company needs to know its cert is queued". The same reasoning arguably applies to its expired history. This is a requirements decision that should be made rather than discovered.

Coverage gaps

Stated plainly, so the pass rate is not read as more than it is.

  1. Import reassignment / overwrite acknowledgement paths. These rewrite existing client rows; exercising them needs a CR, not a smoke run.
  2. Import Undo. The batch id is not scrapeable from the History page markup, so undo was not fired. Cleanup fell through to the Admin-delete backstop, which succeeded.
  3. Partner API v1 contract diff. Requires a live partner API key; not run here. Gate 4 of the pre-deploy checklist covers it via amazon-contract-diff.js.
  4. The certification-type picker widget. Its native <select> is display:none, so the field was set programmatically. The picker's own click behaviour was not exercised.
  5. Two-factor authentication. All six role accounts have 2FA off by design; the 2fatest fixture was not used.
  6. Bulk PDF download / ZIP. Deliberately skipped — bulk sweeps have killed the app pool before.
  7. Browser-side DOM assertions. The Chrome extension lacks read permission for gccwebapp.com, so in-browser verification was screenshot-based. All DOM-level assertions came from the headless run.

How to re-run

Scripts live in Scripts/smoke-prod/_regression/. Preflight is a hard gate — run it first, because grading a gate page produces confident nonsense.

cd Scripts/smoke-prod
node _regression/00-preflight.js         # gate + 6 role logins — run first
node _regression/01-rbac-matrix.js       # 24 routes x 7 roles
node _regression/02-data-scoping.js      # populations + isolation pairs
node _regression/03-exports-downloads.js
node _regression/04-create-edit.js       # WRITES a fixture cert, deletes it in finally
node _regression/06-import.js            # WRITES one imported row, deletes it in finally
node _regression/05-performance.js

Results land as JSON in _regression/_results/; artifacts — CSV exports, the fixture PDF, failure screenshots — in _regression/_artifacts/. Environment overrides: BASE_URL, GATE_PASS, REG_PASSWORD, and REG_HEADLESS=0 to watch it run.

Both write phases create only ZZ_RegressionFixture_* / ZZ_RegressionImport_* rows and remove them in a finally block. If teardown ever fails, the run prints MANUAL CLEANUP REQUIRED with the certificate number. Both fixtures were confirmed removed on this run.
