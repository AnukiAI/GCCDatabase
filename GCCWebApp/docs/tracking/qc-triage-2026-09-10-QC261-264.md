## QC #261 — Edit button should open a new tab (row 270) → **CR-048**

> *"Is it an easy fix (with low risk of breaking things) to have the Edit button open a new tab in
> these views (similar to how Preview does). The team is finding it inefficient by losing their prior
> search when editing a bunch of certs."* — Image 118

**Their instinct about how it is built is right, and it is still easy — just not one line.** Preview
and Edit sit next to each other and differ only in how they navigate:

| | Call |
|---|---|
| Preview | `window.open(withCid('/Certificate/CertificateInternalView/…'), '_blank')` |
| Edit | `window.location.href = withCid('/Certificate/Edit/…')` |

**Every site that has to change** (this is the list the 9/9 draft was missing):

| File | Line | Surface |
|---|---|---|
| `wwwroot/js/certificate-tile-view-internal.js` | 1297 | internal tile + list |
| `wwwroot/js/certificate-tile-view-external.js` | 1279 | external tile + list |
| `wwwroot/js/certificate-tile-view.js` | 1549 | public tile (`editCertificate` exists here too) |
| `Views/Certificate/CertificateInternalView.cshtml` | 492 | internal detail page |
| `Views/Certificate/CertificateExternalView.cshtml` | 411 | external detail page |

Same "each surface carries its own copy" shape as DEF-413. Fixing three and missing two is the
predictable failure here, so treat the table as the checklist.

**Change:** swap `window.location.href = X` for `window.open(X, '_blank')`.

**The `cid` parameter must survive the change, and this is the part to test rather than assume.**
Certificate numbers are **not unique** — 137 numbers span 312 rows — and `cid` is what pins which of
several same-numbered certificates you are editing (DEF-369). `withCid()` already builds it; confirm
in test that it still arrives in the new tab. Getting this wrong means an analyst edits the wrong
certificate silently, which is far worse than the inconvenience being fixed.

**Scope call to make, not to ask:** doing the tile Edits but not the detail-page Edits leaves the same
button behaving two different ways. **Do all five** and tell the client that is what "these views"
was taken to mean.

**One consequence to state, not to fix:** editing in a new tab leaves the original list tab holding a
stale row — save in tab B and tab A still shows old values until refreshed. Preview already behaves
this way, so it is acceptable; say it out loud rather than let them discover it.

**Cost:** 5 one-line changes + viewport pass on both tile views + the `cid` check. **~1.5-2 hr.**
Popup blockers are not a risk — `window.open` inside a click handler is a user gesture, exactly as
Preview does today.

## QC #262 — List view as the default for logged-in users (row 271) → **CR-049**

> *"Is it an easy fix (with low risk of breaking things) to have the List view the default for all
> logged in users. The team will really only use this when they are working and they find it
> inefficient to have to toggle each time the page loads."* — Image 119

**Easy to change. "Low risk" is the client's assumption, and it is the part worth checking.** The
toggle is client-side state with no persistence. The default is hardcoded in two places per view:

- `wwwroot/js/certificate-tile-view-internal.js:27` — `currentView: 'tile'`
- `Views/Certificate/CertificateTileViewInternal.cshtml:263` — `class="toggle-btn active"` and
  `aria-pressed="true"` on the Tile button
- the external view repeats both (`…-external.js:27`, `CertificateTileViewExternal.cshtml:195`)

The **public** view has no toggle at all, so it is untouched — which correctly matches "logged in
users".

**The risk is first paint, not the toggle.** List view has only ever been reached by clicking, i.e.
*after* certificates are loaded. `showTableView()` does have a cold branch
(`if (!state.certificates || state.certificates.length === 0) await loadCertificates()`), so the path
exists — but it has never been the initial render in production. Infinite scroll, column-visibility
restore from `localStorage`, and the sticky header all initialise in tile context today. **That needs
an actual test, not an inspection**, and it is where the time goes.

**The 9/9 draft's (a)-vs-(b) framing is right and worth keeping.** A hard default just reassigns the
toggling to whoever prefers tiles; remembering each person's last choice (the pattern the
column-visibility code on this same page already uses) solves it permanently. Recommend (b), ~+0.5 hr.

**Scope question that must be asked before building.** "All logged in users" literally includes
**External company and partner users**, but *"the team will really only use this when they are
working"* says they are picturing staff. Defaulting a customer-facing view to a dense data table is a
different decision. **Recommend internal only, and confirm.** Building both and being wrong costs the
same again.

**Cost:** ~2 lines per view plus first-paint verification. **~1.5-2 hr** internal only; ~2.5 hr if
external is included; +0.5 hr for the remembered-choice variant.

## QC #263 — Cert Import template: the Certificate # column (row 272) → **DEF-418**

> *"…The template has a Certificate # column. When left blank it assigns a number, which is right. Is
> the column there in the case you want to make an edit to a current one…? I think we need to update
> the below text to be more detailed… right now its saying Cert Number is required when its not when
> adding NEW entries."* — Image 120

**Two separate things. The first costs nothing; the second is a real defect and is bigger than they
noticed.**

### Part 1 — their question. Answer: yes, exactly that. No work.

Confirmed in code, both branches:

- **Blank** → `row.WillAutoAssignNumber = true` (`Services/Import/CertificateImportService.cs:1351`);
  at apply time `GenerateNextCertificateNumberAsync()` mints the next number (`:1854`). Several blank
  rows in one file each get their own number instead of colliding.
- **Supplied** → the row matches the existing certificate of that number and **updates it** (`:1637`),
  behind an explicit overwrite confirmation that takes a safety backup first (CR-023 R5,
  `CertificateImportController.cs:151-171`).

The code even says so in as many words at `:1340`: *"Certificate # is deliberately NOT required."*

**Keep the 9/9 draft's duplicate-number warning — it is correct and I re-verified it.** The match is
`existingCerts.FirstOrDefault(...)`, so where a number spans several certificates the import updates
**the first one it finds**, which may not be the intended one. Worth offering a guard that stops and
warns on an ambiguous number, as a separate small CR, *if* the team is going to use the template
routinely for edits.

**Also worth telling them, given their note that they didn't want to test against real data:** the
preview screen shows a field-by-field diff and nothing is written until someone approves it. That is
the reassurance the question is really asking for.

### Part 2 — the help text is wrong in four places, and contradicts itself. **DEF.**

The client spotted one wrong line. `Views/CertificateImport/Index.cshtml`:

| Line | Says | Actually |
|---|---|---|
| **72** | *"Required Columns: CertificateNumber, CompanyName, ProductName, CertificationType"* | **CertificateNumber is explicitly NOT required** (`:1340`). The other three are. |
| **74** | *"Validation: Company, Product, and CertificationType must exist in database"* | **Wrong for Company and Product** — both are auto-created on import (`:668-745`, *"Auto-created via certificate import"*). Correct for Certification Type only (`:1527`). |
| **127-131** | The same list again, headed *"Required Columns"* | The same two errors restated. |
| **128-131** | Column names as `CERTIFICATE_NUMBER`, `COMPANY_NAME`, … | **Not wrong** — these are genuine accepted aliases (`:78-89`). But they are **not the headers the Download Template button emits** (`Certificate #`, `Company`, `Product Name`, `Certification Type`), so the page documents a format the template does not produce. |

**Line 74 and line 128 contradict each other on the same page** about whether companies and products
must pre-exist — and the one people read first is the wrong one.

**Nothing on the page describes** blank = auto-assign, supplied = update, or the overwrite
confirmation. That is precisely the client's request.

**Cost:** rewrite both panels against the code, align the documented column names with what the
template emits, add the create-vs-update explanation. Copy only, no logic. **~1-1.5 hr.**
Cites QC #263.

## Numbering note — read before claiming any of these

**`^### DEF-` undercounts.** It tops out at DEF-413, but **DEF-414 through DEF-417 exist as `####`
headings** (`defect-register.md:14716, 14888, 15015, 15032`). Real high-water is **DEF-417 / CR-046**.
Grep `^#{2,5} DEF-[0-9]+`, not `^### DEF-`. This is not hypothetical — it is exactly how the 9/9 draft
came to reserve DEF-416 after it had already been used the same day.

**CR-047 is verbally earmarked.** `DEF-413-subcategory-filter-as-is-to-be.md` §7 reserves it for the
three orphan subcategory names (Zero Waste to Landfill, Waste Diversion Event, Waste System Audit).
No register row was ever written, so it is technically free — but honour the earmark or deliberately
release it, once rather than twice. The 9/9 draft skipped it correctly.
