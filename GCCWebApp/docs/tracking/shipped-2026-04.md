## DEF-100 — Tile list/table view: lazy-load no longer wipes earlier pages (2026-04-26)

On both the analyst (internal) and partner (external) certificate tile pages, switching to **list/table view** and scrolling to load the next page replaced the previously rendered rows with only the new page — so users only ever saw "the remainder, not the whole of the dataset". Tile/card view was unaffected (it correctly used `insertAdjacentHTML('beforeend', …)`); the table-view code path mistakenly called a full-render helper (`renderTableRows`) that does `gridBody.innerHTML = …`, so passing only the new page wiped every previously rendered row. Fix: the list-view append branch now builds HTML for new rows only and appends them directly to `#gridBody`. Also re-attaches `change` listeners on the new `.row-checkbox` elements so bulk-selection on later pages still drives the bulk-actions bar, re-applies column-toggle visibility so newly-loaded rows respect the user's hidden-columns settings, and re-syncs the sticky-header scroll bar via `requestAnimationFrame(syncScrollSizes)`. Files: `wwwroot/js/certificate-tile-view-internal.js`, `wwwroot/js/certificate-tile-view-external.js`. Public tile view (`certificate-tile-view.js`) was already structurally correct (it re-renders the full list). Build: 0 errors, 0 warnings. Logged as DEF-100; verification post-deploy is to scroll past the page boundary on table view and confirm row count grows monotonically.

## DEF-112 — Stop auto-generating placeholder PDFs (2026-04-26)

When a certificate had no uploaded PDF, hitting Download returned a freshly-generated placeholder PDF instead of failing — misleading analysts and partners (it implied a real cert exists when it doesn't). Three download paths fell through to `_pdfService.GenerateCertificatePdfAsync()`: `/Certificate/Download/{n}` (the route every UI download button hits), `/api/certificate-tiles/{id}/download` (always generated, never even checked for a file), and `Services/CertificateService.GetCertificateDownloadAsync` (called by `/api/certificates/{id}/download`). All three now return HTTP 404 when `Certificate.CertificateFile` is null/empty or the file is missing on disk. Partner API `/api/v1/certificates/{id}/download` was already correct (returns 404 with a TODO comment) — left untouched per the immutable-Partner-API rule. Verified: cert WITH file returns 200 + 2.4MB PDF; cert WITHOUT file returns 404. Follow-up flagged: list-view download buttons are still clickable for fileless certs (will open a 404 in a new tab), since neither the public nor internal list API surfaces a `hasPdf` indicator yet.

## DEF-106 — Partner API single-cert endpoints now scope by partner (security: cross-tenant leak fixed, 2026-05-01, delivered in the 2026-08-04 build)

Found during TC-QC-143 (CR-008 Partner Role) execution. The Partner API LIST endpoint had correctly filtered `userPartnerNames.Contains(c.Partner)` since 2026-04-21, but the **four single-cert endpoints (`GET /api/v1/certificates/{id}`, `/number/{n}`, `/gs1/{n}`, `/{id}/download`) had no such check** — they only enforced role + `PublicStatuses`, never matched the cert's partner against the caller's. Empirically confirmed: the Amazon Partner API key successfully fetched Novi cert `EXT-NOVI-001` via all three read endpoints — full payloads with `"partner": "Novi"` returned to Amazon. Cross-partner data exposure. Fix: added `userPartnerNames.Contains(cert.Partner ?? "None")` check in each of the four endpoints, after the existing PublicStatuses check; generic 404 on fail (no enumeration leak). Verified locally: 3 positive (Amazon→Amazon) + 4 negative (Amazon→Novi all 404) + 1 regression check (LIST still returns 4 Amazon certs). Same fix covers Partner-role app users on cookie auth — they share the `GetCurrentUserPartnerNamesAsync()` and `GetCurrentUserRole() == "Partner"` paths. **Coordinate deploy with DEF-103** — touches the same four endpoints. **High severity** — partner data isolation is a contract expectation. Heads-up to the client recommended before deploy.

## CR-015 — Product ID status follows parent cert (2026-04-30, built locally — pending deploy)

Shawn raised this on the 2026-04-30 status conversation after talking through Amazon badging with the client: per-row product ID Status was a free-text field that defaulted to `"Active"` and never auto-changed when the parent cert moved out of an active state, so an analyst (or the seeded data) could leave an ASIN tagged Active even after its cert expired or moved to Hold. Risk was specifically Amazon badging — Amazon's contract reads each cert's product identifiers and a stale Active flag could show a product as still certified when it shouldn't. Live impact today is muted because the Partner API list endpoint already filters out non-public certs (DEF-097, 2026-04-21), so Amazon never actually sees the stale rows; this CR cleans the underlying state to match. Built 2026-04-30 to the rule **product ID Status = "Active" iff parent cert is in `PublicStatuses` (`Client Approved - Paid` or `Republished`), else "Inactive"**. Cascade fires on every cert-status-change path: manual edit, create POST, bulk update, workflow transition, auto-expire, CSV import (both create and update branches), and product-ID create/edit. Status is no longer user-controlled — Status column removed from the Product ID list, the filter row, the Add/Edit modal, the CSV import template, and the in-memory CSV export. Sample-CSV API endpoint also drops the column. CSV imports that still carry a Status header are silently ignored (back-compat). No DB schema change; column kept for historical audit and to avoid a destructive migration. SQL backfill script staged at `Scripts/database/CR015_backfill_product_id_status.sql` — idempotent, transaction-wrapped, with pre-flight + post-flight verification queries in the header. Ran against dev DB (`ANUKI01.GCCDatabase_Dev`): 12 product IDs flipped to Inactive (those 12 sit on certs in legacy `Active` status that never migrated to `Client Approved - Paid` — the orphaned set noted in memory 2026-04-30); 0 needed flip to Active; post-backfill audit returned 0 mismatches. Files: `Models/CertificateProductId.cs` (helper), `Services/ProductIdService.cs` (cascade method + create/update overrides + import Status drop), `Services/CertificateService.cs` + `CertificateExpirationService.cs` + `CertificateWorkflowService.cs` + `Services/Import/CertificateImportService.cs` (cascade calls), `Controllers/CertificateController.cs` (DI + cascade on Edit/Create/Import), `Controllers/Api/ProductIdApiController.cs` (sample CSV), `Views/Shared/_ProductIdManager.cshtml` + `wwwroot/js/product-id-manager.js` (UI removal). Test-project constructors updated for new DI parameter. Build: 0 errors. `dotnet test`: 143/144 (the 1 remaining failure is a pre-existing dead-code test for `CheckAndUpdateExpiringCertificatesAsync` referencing pre-8-state status strings — fails on master too, not introduced by this CR; verified via git stash baseline). Tracked as **DEF-104** in the defect register and **CR-015** in the change-request register. Pre-deploy: run the backfill script once after the app deploys; pre-flight query in the script header tells you the row count before the flip. **Partner API contract preserved** — `feedback_amazon_api_immutable.md` rule honored.
