Tag the certificates first, or the partner sees nothing

An API key on its own returns an empty list. What a partner receives is decided by two separate checks, and the certificate tagging is the one people forget. Work through the steps in the order given below.

1  What you are setting up

A partner is an external organisation — Amazon, Novi, or another — that pulls certificate data from GCC over the Partner API. Setting one up has four parts, and all four are yours to do. You do not need to raise a request with Anuki for any of them.

StepWhat it doesWhere
1. Create the partner recordGives the organisation an identity in the systemAdministration → Partners
2. Tag certificates to the partnerDecides which certificates they may receiveOn each certificate
3. Generate an API keyGives them a credential tied to that partnerAdministration → Partner API Access
4. Test, then deliver the keyProves it works before the partner tries itTerminal, then secure channel

1.1 The two checks that decide what a partner sees

This is the single most useful thing to understand, because almost every "the feed is empty" or "why can't they see this certificate" question comes back to it.

  1. Is the certificate tagged to that partner? If not, it reaches nobody — regardless of status.
  2. Is the certificate commercially in force? Its status must be Client Approved – Paid, Client

Approved – Confidential, or Republished, and today's date must fall inside its effective and expiration dates.

Both must be true. The checks are independent, so a perfectly valid certificate that nobody tagged is invisible, and a tagged certificate that has expired is equally invisible.

Confidential certificates DO go to partners

Confidential is an embargo on the public website only. Those certificates are paid, in-force work and they are still sent to partners and still badged. Do not assume Confidential means withheld from everyone.

2  Create the partner record

  1. Sign in as an Administrator.
  2. Go to Administration → Partners.
  1. Click Add. A new editable row appears at the top of the table — this is an inline row, not a

pop-up dialog.

  1. Enter the Partner Name. It must be unique and is limited to 100 characters. This exact name

is what the partner sees returned in the `partner` field of their API responses, so spell it the way you want it to appear.

  1. Add a Description if useful — free text, up to 500 characters.
  2. Save the row. New partners are Active by default.
Deactivating a partner does NOT cut off their API access

This is worth knowing before you rely on it. Setting a partner to inactive does not stop their API keys from working — the key check does not consult the partner's Active flag. The only way to stop a partner calling the API is to revoke each of their keys (section 7). Deactivating affects where the partner appears in the application, not their API access.

3  Tag the certificates

A partner receives only the certificates explicitly associated with them. Open each certificate that should be included and add the partner in its Partners field.

For certificates that carry product identifiers — ASINs, UPCs, GTINs and so on — identifiers behave slightly differently from the certificate itself:

Identifier is tagged toDoes this partner receive it?
NobodyYes — untagged identifiers are treated as shared
This partnerYes
A different partner onlyNo — it is withheld

That last row is deliberate. Two partners can share a certificate without either of them seeing the other's product identifiers.

4  Generate the API key

  1. Go to Administration → Partner API Access.
  1. Click Generate API Key. A dialog opens with three fields.
  1. Choose the Partner. This is the only required field, and it is what scopes the key.
  2. Enter a Description. Optional, and internal only — something like "Amazon production" or

"Amazon test" so you can tell keys apart later.

  1. Set an Expiration Date. Optional. Leave it blank for a key that never expires; set a date for

a time-boxed test key.

  1. Click Generate Key. The new key is shown with a copy button. Copy it now — see the

warning below.

Keys are 76 characters: the prefix `gcc_partner_` followed by 64 hexadecimal characters.

Copy the key before you close that dialog — it is shown only once

This is the only moment the full key is visible. Afterwards the list shows every key masked, and the only action on each row is Revoke. There is no way to retrieve the value later. If you close the dialog without copying it, the key is unusable: revoke it and generate a replacement. Paste it somewhere safe before you click away.

4.1 What you cannot set per key

Two values that look configurable are not. They are system-wide, and there is no field for either on the key:

SettingValuePer key?
Rate limit200 requests per hourNo — the same for every partner
Endpoints permittedAll endpointsNo — keys are not scoped to a subset

So only three things genuinely vary between partners: the partner name, the key itself, and the key's expiry date.

5  Which address the partner uses

EnvironmentBase URLStatus
Test`https://dbtest.greencirclecertified.com/api/v1`Live now — use for all integration work
Production`https://database.greencirclecertified.com/api/v1`At go-live only

Partners should build against the test address and change the hostname at go-live. Nothing else changes — the paths, the `X-API-Key` header and the response are identical.

The production address is not live yet

`database.greencirclecertified.com` still serves the previous certificate database. Do not give it to a partner as a working address before cutover is confirmed.

6  Test the key before you hand it over

Always prove the key works yourself first. A partner hitting a problem on day one costs far more time than this check.

  1. Open a terminal and run the request below, substituting the key.
  2. Read the response code before anything else.

``` curl -i -H "X-API-Key: gcc_partner_..." https://dbtest.greencirclecertified.com/api/v1/certificates ```

ResponseWhat it meansWhat to do
`200` with certificatesThe key worksDeliver it
`200` with an empty listThe key is fine; nothing is tagged to that partnerGo back to section 3
`401`Key wrong, revoked, or expiredCheck the key row is still active
`429`Rate limit hit — 200 requests in the last hourWait, then retry
Do not test by pasting the URL into a browser where you are already signed in

A signed-in session takes priority over the API key, so the page may load perfectly while the key itself is invalid. The result tells you nothing. Use a terminal, or a private browsing window.

Responses are cached for five minutes. If you tag a certificate and immediately re-test, wait five minutes before concluding that something is wrong.

6.1 Delivering the key

Send the key by a secure channel — a password manager share, or another route your organisation already trusts for credentials. Never paste it into the Integration Guide, an email body, or a chat message. The Integration Guide gets forwarded inside partner organisations, and a key printed in it is a key you will have to rotate.

7  Revoking and rotating a key

Use Revoke on the key's row. It takes effect immediately and cannot be undone — every request using that key starts returning `401`. Revoked keys are retained for audit.

Revoke a key when the partner no longer needs access, when a key may have been exposed, when you issue the production key and the test key is no longer needed, or as part of routine rotation.

To rotate without an outage, generate the new key first, give the partner time to switch, then revoke the old one. Both keys work while the changeover happens.

8  What the partner receives
CertificatesOnly those tagged to them, and only while in force
Status fieldAlways the literal string "Active" — internal status names are never exposed
Product identifiersUntagged ones, plus those tagged to them
Internal tagsNever returned
External tagsReturned
Analyst notes, audit historyNever returned

The API expresses validity by presence, not by a status value. A certificate that is no longer in force does not appear with an "expired" status — it stops appearing at all. Partners should treat disappearance as authoritative, and should not wait for a status change that will never arrive.

8.1 The endpoints

EndpointPurpose

`GET /certificates/number/{number}`One certificate by its certificate number
`GET /certificates/search`Search by term, company, type or date range
`GET /certificates/search/productid`Find certificates by product identifier such as an ASIN

9  Troubleshooting

SymptomAlmost always
Partner sees an empty listNo certificates tagged to that partner — section 3
A specific certificate is missingNot tagged, expired, not yet effective, or still in draft
`401` on every requestKey revoked or expired; check the key row
`403` on one pathThe endpoint is outside what that key may call
`429`200-per-hour rate limit reached
Partner sees a certificate you expected to be privateConfidential is embargoed from the public site only — it still reaches partners
Changes not showingFive-minute response cache; wait it out

If a partner asks why a particular certificate is not visible, tell them rather than letting them infer it. The API deliberately makes "expired", "not tagged to you" and "never existed" look identical, so that a key cannot be used to probe for certificates outside its scope. That is by design, and it means the partner genuinely cannot work it out from the response.

10  Appendix — filling in a partner's "Your Connection" panel

The Partner Integration Guide — the document sent to the partner's engineering team — opens with a panel headed Your Connection, introduced as *"values specific to the key issued to you."* Filling it in is the last step before issuing that guide, and it is where nearly every question about partner setup has come from.

The panel overstates how much varies. It reads as eight or nine values to look up per partner. Only three actually change between partners. The rest are the same for everybody, and two of them cannot be configured per key at all — there is no field for them anywhere in the application.

10.1 Row by row

Row in the panelWhere the value comes fromVaries per partner?
Partner nameThe Partner record you created in section 2 — spelled exactly as storedYes

Key expirationThe Expiration Date field in that dialog; blank means neverYes
Base URLFixed. `https://database.greencirclecertified.com/api/v1`, at go-liveNo
Test base URLFixed. `https://dbtest.greencirclecertified.com/api/v1`, live nowNo
Rate limitSystem-wide: 200 requests per hour. No per-key field existsNo
Endpoints permittedAll endpoints. Keys are not scoped to a subsetNo
Certificate status modeAlways *Presence* — validity is expressed by whether a certificate is returned at all. See section 8No
Product identifier scopeFixed: identifiers tagged to nobody, plus those tagged to this partner. See section 3No
Two rows used to carry an instruction that could not be followed

Earlier revisions of the Integration Guide told the issuer to *"check the rate limit and permitted endpoints against the API key actually issued to that partner."* There is nothing on the key to check them against — both are system-wide. If you are working from an older copy of that guide, ignore that instruction; the current template has the two values pre-filled as the constants they are.

10.2 The questions this panel keeps producing

  1. "Where do we get the API key — does this have to be requested from the developer?" No. You

generate it yourself in Administration → Partner API Access. Section 4 of this guide is the whole procedure.

  1. "Where would this information come from?" — asked against the rate limit, the endpoint scope,

the status mode and the key expiry. Of those four, only the expiry is something you choose; see the table above.

  1. "Can the partner name be whatever we enter, or does it have to match something in the key?" It

must match. The value the partner receives in the `partner` field is the Partner record's name as held in the database, and that same name decides which certificates the key can see. It is not a free-text label.

  1. "After go-live, does the test address stay or is it production only?" Both, depending on the

partner's stage. During onboarding the partner works against the test address. Once they are live, their copy of the guide should mark that row as no longer applicable — a live test address left in a document that gets forwarded internally invites somebody to build against the wrong environment. The test environment itself stays, because the next partner needs it.

  1. "Is `amazonCode` relevant to anyone but Amazon — should it be removed?" Keep it. That field is

returned in the payload to every partner, not only Amazon. Removing it from the field table would leave a partner looking at a field in the JSON that the documentation never mentions.

  1. "Who does the onboarding checklist's Owner column refer to?" It should read GCC in the

partner-facing copy — GreenCircle is the partner's counterparty. Internally, the steps that were historically done by the developer are issuing the test and production keys, and those are the screens documented in section 4.

Never paste a live key into the Integration Guide

That document is circulated by email and forwarded inside partner organisations. A key printed in it is a key you will have to rotate. The API key row should describe the format and say the key is delivered separately — which is what the current template does.
