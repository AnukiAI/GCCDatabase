7/1/26 - Testing:

completed: Bug: Apostrophe encoding error in filters/search: Selecting companies with apostrophes in their name (e.g., "Gemma's Company Co.") via the search autocomplete or the Company checkbox triggers a "Failed to load certificates" error. The URL contains %27 for the apostrophe, but the server fails to handle this. Affected paths: search autocomplete selection and the Company filter checkbox.


 Summary of this task

  Fix (working tree, no commit):
  - Middleware/SecurityHeadersMiddleware.cs — decode the query string before  injection matching; removed the false-positive %27/%22 tokens.

  Tracking:
  - docs/tracking/defect-register.md — DEF-301 added (Symptom / Root cause /  Fix / Verification / Linked memory), next number after DEF-300.
  - docs/tracking/shipped-2026-07.md — created (July didn't exist yet) with
  the DEF-301 delivery row, matching June's stakeholder-readable format.

  Verified on localhost:5101:
  - Apostrophe company filter + O'Brien search → HTTP 200 (were 400)
  - Genuine injection payloads → HTTP 400, still blocked

  Flagged for the deploy: this is code-only, no migration (Gate 7 no-op).
  The same middleware runs in prod, so any existing certs with apostrophe
  company names are broken there today and self-resolve the moment this
  ships — worth bundling into the next rebuild rather than holding.

  One thing I left for you to decide: I did not touch the
  pathInjectionPatterns list (path is already framework-decoded and company
  values never travel in the URL path, so it's not a false-positive risk) —
  but if you'd prefer the same cleanup applied there for consistency, say
  the word.
