1. Quick Start

Three steps to get your first data:

1 Get your API key from GCC (format: gcc_partner_[hash]). This full string, including the gcc_partner_ prefix, is your X-API-Key value — use it exactly as provided in the header.

2 Make your first request:

# Test environment (current)
curl -X GET "https://gccwebapp.com/api/v1/certificates/gs1" \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Accept: application/json"

# Production environment (pending DNS configuration)
curl -X GET "https://greencirclecertified.com/database/api/v1/certificates/gs1" \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Accept: application/json"

3 You'll receive a JSON response with all active certificates tagged to your partner account, including ASINs, certification details, and PDF download links.

Integration model: You PULL data from GCC. GCC does not push to you. Call the API on your schedule to retrieve current certification data. Each API call returns the active certificate database. Amazon is responsible for identifying what is new or removed on their side to badge and unbadge products accordingly.

7. Pagination

How It Works

The API paginates by certificate, not by product or ASIN. Each page returns up to 100 certificates per request, and each certificate includes all of its associated ASINs and product identifiers in a single response — product IDs are never split across pages.

Example: If a single certificate covers 50 ASINs, all 50 ASINs are returned with that certificate in one response. A page of 100 certificates could contain thousands of ASINs.

Capacity

ParameterValue
Max certificates per page100
Partner API rate limit200 calls/hour
Max certificates per hour20,000 (200 calls × 100 per page)
ASINs per certificateUnlimited — all included in the response

For example, if Amazon has 300 active certificates covering 11,000+ ASINs, that requires only 3 API calls (3 pages × 100 certificates) to retrieve the complete dataset — well within the 200 calls/hour limit. Rate limits reset at the top of each hour.

Pagination Example

// Page 1
GET /api/v1/certificates?pageNumber=1&pageSize=100

// Check response
"pagination": {
  "totalCount": 250,
  "pageNumber": 1,
  "pageSize": 100,
  "totalPages": 3,
  "hasNext": true,      // ← more pages available
  "hasPrevious": false
}

// Page 2
GET /api/v1/certificates?pageNumber=2&pageSize=100

// Continue until hasNext is false

Loop until hasNext is false to retrieve all certificates.

Page size & rate limits are configurable. The default maximum of 100 certificates per page and 200 API calls per hour are suitable for most integration scenarios. If your volume requires higher throughput, contact GCC support to adjust these limits for your API key.

Appendix A: GS1 JSON-LD Format Reference

Why Two Response Formats?

The GCC API provides two response formats for certificate data:

FormatEndpointPurpose
Standard JSON/certificatesGCC's own field naming convention. Simple and direct.
GS1 JSON-LD/certificates/gs1Follows the GS1 Certification Data Model specification. Industry-standard format for interoperability.

Both formats return the same underlying data. The difference is the field names and structure.

What is GS1?

GS1 is the global standards organization that governs product identification across the supply chain — including UPC barcodes, GTINs, and EAN codes used by over 2 million companies worldwide. GS1 is a not-for-profit headquartered in Brussels with member organizations in over 110 countries.

GS1 US, the American member organization, published the Certification Data Model — a standardized format for exchanging product certification information between certification bodies and retailers. This is the specification the /certificates/gs1 endpoint follows.

Why Do the GS1 Field Names Differ from Standard JSON?

The GS1 JSON-LD format uses field names defined by the GS1 Web Vocabulary, a formal specification maintained by GS1 Global. These field names cannot be changed because:

  • The response references a published JSON Schema (cert_schema.json) and JSON-LD context (cert_context.json) hosted by GS1 US
  • The schema enforces required field names, data types, and validation rules (e.g., gtin must be exactly 14 digits, status must be ACTIVE or INACTIVE)
  • Any consumer validating against the schema would reject or ignore non-standard field names
  • JSON-LD consumers map field names to GS1 vocabulary URIs — renamed fields would lose their semantic meaning
